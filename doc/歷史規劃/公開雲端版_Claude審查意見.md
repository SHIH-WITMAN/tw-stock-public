# 公開雲端版規劃｜Claude 交叉審查意見

**審查者** Claude　**日期** 2026-11-23　**對照版本** 台股管家 v2.27.0（`app_paths.py`）
**審查對象** [公開雲端版_規劃書](公開雲端版_規劃書.md)、[Codex 審查與改善方案](公開雲端版_Codex審查與改善方案.md)
**證據範圍** 本機原始碼閱讀、隔離的純函式重跑（未匯入 Flask、未碰正式資料庫）、審查日公開網頁。未實測任何雲端服務或官方 API 的連線穩定度。

---

## 0. 結論先講

1. **規劃書方向正確**（盤後批次 → 靜態 JSON → CDN → 瀏覽器計算），但它把「本機版已驗證」當成移植前提，而原始碼裡至少有 **3 個會直接污染公開排行的缺陷**（§2），規劃書描述的部分行為與程式不符。
2. **Codex 審查品質很高**，資料授權、FinMind 再散布限制、版本化 manifest、反例驅動測試等主張我都同意。我補強兩點：它的 XIRR 反例其實低估了問題，以及它的治理清單對單人維運太重，需要排優先序（§4）。
3. **兩份文件都漏掉一個關鍵架構簡化**：含息趨勢與 ETF 年度比較可以在 Python 端預產「每檔總報酬指數」，瀏覽器只做除法（§3-1，已用原函式數值驗證）。這能把「Python → TypeScript 雙引擎一致性」的工作量砍到只剩回測頁，也是本次我最建議採納的修改。
4. 以使用者預估的百人規模，**免費額度不是風險，資料正確性與維運量能才是**。真正會讓專案失敗的是：公司事件漏抓造成假暴漲暴跌、上游格式改版無人察覺、以及單人同時維護兩套程式。

## 2. 原始碼核實發現（規劃書假設「已驗證」，實際不成立）

### 2-1. XIRR 求解器永遠不回報失敗 → 「近似值不參與排序」是死程式碼（**嚴重，Codex 低估**）

[`core_engine.py` `solve_xirr`](../core_engine.py) 做 100 次二分後**無條件回傳區間中點**，從不回傳 `None`。[`calculate_dca_stock_backtest`](../flask_app/api/watchlist_api.py) 只在 `None／NaN／inf` 時才改用近似算法並標記 `approximation`，因此該分支實際上不會觸發；前端 `backtest_compare.js` 依 `cagr_method==='approximation'` 排除排序的邏輯也就永遠不生效。

以原函式邏輯隔離重跑：

| 現金流（金額／年數） | 回傳年化 | 回傳點的殘差（應趨近 0） |
|---|---:|---:|
| 同日 `[-100, 100]`／`[0, 0]`（Codex 反例） | −49.995% | 0（任何利率都成立） |
| 全損 `[-100, 0]`／`[0, 1]` | −99.99% | −100 |
| 短期暴漲 `[-100, 300]`／`[0, 0.02]` | **+100000%** | 161 |
| 多次變號 `[-100, 230, -132]`／`[0, 1, 2]` | −99.99% | −1.3×10¹⁰ |
| 正常 `[-100, 110]`／`[0, 1]` | 9.9999% | ≈0 |

**影響**：公開版一旦有短期或極端的 DCA 組合，+100000% 會進入年化排序主欄。
**修改建議**：求解器回傳 `(rate, status)`；結束時以殘差相對於總流量的比例判定收斂，碰到區間邊界視為失敗；同日流量先合併；全負或全正直接判定無解。公開版年化欄**持有未滿 1 年一律不顯示年化**（業界慣例，也避免短期年化誤導大眾）。

### 2-2. 單筆回測把除息日當天收盤買入計入股息（確認 Codex 反例 1）

`calculate_single_stock_backtest` 中，分割用 `buy_date < sp_date`，除息卻用 `buy_date <= ex_str`，兩者不一致；除息日收盤才買進的人沒有該次權利。DCA 版本因 `DIVIDEND` 優先序先於 `BUY`，結果正確。**修正方式**：條件改成 `buy_date < ex_str`；本機版也應一併修（屬一般缺陷修復，不涉及第 6／7／12 項）。

### 2-3. 減資完全沒有進入三個公開模組的計算（**嚴重，兩份都未明說**）

- [`return_trend.py`](../flask_app/services/return_trend.py) 只讀 `TaiwanStockSplitPrice`，事件只有 split／cash／stock 三種。
- [`public_cashflow.market_metrics`](../flask_app/services/public_cashflow.py)（ETF 滾動報酬）與兩種回測同樣沒有減資事件。
- 全專案只有 `technical_radar.py` 讀 `TaiwanStockCapitalReductionReferencePrice`，用途是技術線圖的價格基準調整，不是總報酬計算。

規劃書 §2-1 與設計決策紀錄的含息趨勢段落把「減資換股」列為「停牌日記 null、自動銜接」，但**只處理了停牌日，沒有處理股數變化**。以現金減資 30% 為例：復牌後股價約上漲 1/0.7−1 ≈ 43%，股數卻沒有乘以 0.7，退還的現金也沒有入帳，圖上就會出現一段假性暴漲。個股池收錄 200～300 檔時，這種情況在 5 年內幾乎必然遇到。

**修改建議**：Phase 1 個股池先限縮為 ETF＋少數權值股，並對池內所有標的做 5 年減資／分割人工清查；公司事件改走 §3-3 的參考價閘門。

### 2-4. 債券型與國外成分 ETF 一律對比台股加權報酬指數

[`etf_observation.calendar_comparisons`](../flask_app/services/etf_observation.py) 對所有 ETF 都以 `TAIEX` 報酬指數為基準。本機個人使用時無妨，但公開版的「年度勝大盤次數」若套用在美債 ETF 上，是在比不同資產類別。一般讀者容易誤讀成「債券 ETF 表現差」或「某年勝過大盤所以比較好」。
**修改建議**：勝大盤欄位只對「台股股票型」顯示；債券型、國外成分改顯示「同類別中位數」或不顯示，並在分類篩選處註明基準。

### 2-5. 規劃書描述與程式或事實不符的小項

| 規劃書位置 | 描述 | 實際 |
|---|---|---|
| §2-3、§4-3-3 | 求解失敗的近似值只放明細 | 見 2-1，不會發生 |
| §4-2 表 | TWSE `STOCK_DAY_ALL` 每日 1 次 | OpenAPI 只提供最新一日；5 年回填需改用其他歷史端點，授權另議（Codex 已指出） |
| §4-2 健檢 | 單日 ±25% 才警示 | 國內成分股票／ETF 有 ±10% 漲跌幅，超過即異常；國外成分 ETF 依證交所說明**無漲跌幅限制**，同一門檻兩邊都不適用 |
| §4-2 個股除權息 | 「缺發放日以預設 30 天估算」 | 本機 30 天來自個人設定 `預設配息入帳天數`；公開版需寫死並標示。個股**發放日**的官方開放來源尚未確認（見 §3-4） |
| §4-3-1 | 移植 return_trend 的 `MAX_SERIES` 等 | 主軸日期採各序列觀測日聯集；全體同日缺漏時該日消失（Codex 已指出），公開版應改用交易所日曆作主軸 |

## 3. 兩份文件都沒提到的盲點與建議

### 3-1. 【最重要】預產「總報酬指數」，瀏覽器只做除法

`compute_series` 的含息模型（除息日收盤以零碎股再投入、分割與配股乘股數）是**乘法、與起始股數無關**的過程。因此，任一起算日 s 到 t 的報酬，等於「自最早日起算的單一累積指數」相除：

> R(s, t) = TRI(t) ÷ TRI(s) − 1

我以原 `compute_series` 函式、900 個交易日的合成資料（含 19 次配息、1 拆 4 分割、同日配股加配息）、60 個隨機起算日驗證，兩種口徑的最大差異都在 **0.0002 個百分點以內**，全部來自原函式本身的四捨五入。

**這代表**：
- Python 盤後管線為每檔產出 `close[]`、`tri[]`（含息）、`pri[]`（價差，已調整分割／配股）三條與交易日曆對齊的陣列，停牌日為 `null`；「缺除息日收盤」等不可計算區段以斷點旗標表示。
- 含息趨勢頁、ETF 曆年度報酬、年度勝大盤、整段超額，**全部變成陣列除法**，瀏覽器端不需要任何公司事件邏輯。
- 需要用 TypeScript 移植的只剩**單筆／DCA 回測**（發放日 DRIP、0.01 股取整、XIRR），一致性驗證範圍大幅縮小。
- 公司事件只在 Python 一處處理，修正一次，全站生效。

### 3-2. 同一站內的雙引擎不一致

規劃書 §5-3 的 `catalog.json` 由 Python「預先算好 1Y／年度績效」，含息趨勢卻由 TypeScript 即時計算。同一檔 ETF 在 ETF 頁與趨勢頁可能顯示不同的報酬數字，公開網站上這會直接傷害可信度。採用 3-1 後兩者共用同一條 `tri[]`，問題自然消失；回測若仍需 TypeScript 引擎，可在管線中用 Node 跑**同一份 TS 程式碼**預產熱門範本，不另寫 Python 版本。

### 3-3. 用官方「參考價」取代 ±25% 門檻作為事件閘門

交易所在除權息、減資、分割恢復交易時會公布開盤參考價。**只要「參考價 ≠ 前一日收盤」而事件表沒有對應紀錄，就代表漏了事件**，這是確定性的判斷，比價格跳動門檻可靠得多，也不受漲跌幅制度差異影響。建議 Phase 0 探測 TWSE／TPEx 的除權除息計算結果表與減資恢復買賣參考價表，作為發布閘門的必要檢查；價格跳動檢查保留為輔助提示，並依「國內成分±10%／國外成分無限制」分別設定門檻。

### 3-4. 個股「發放日」可能是最弱的一環

回測採發放日 DRIP，ETF 發放日可從 TDCC 取得（Codex 指出其開放資料版本），但上市櫃**個股**的現金股利發放日，目前本機實際依賴 FinMind（源頭是公開資訊觀測站）。若公開版移除 FinMind，個股回測可能大量落入「預設 30 天估算」。
**建議**：Phase 0 先確認個股發放日的授權來源；未確認前，**回測頁只開放 ETF**，個股只提供含息趨勢（含息趨勢採除息日再投入，不需發放日）。

### 3-5. 法規面：投顧法與個資法（非法律意見，建議請教專業人士）

- **證券投資信託及顧問法**：未經許可對有價證券提供分析意見或推介建議並獲取報酬，可能構成非法經營投顧業務。近年判決以是否「因而獲得對價報酬」與「客觀上有推介效果」為判斷重點（例：[臺灣士林地方法院 114 年度金訴字第 668 號刑事判決](https://judgment.judicial.gov.tw/FILES/SCDM/114%2c%e9%87%91%e8%a8%b4%2c668%2c20260605%2c1.pdf)）。免費、無廣告、使用者自選條件的歷史數據工具風險相對低，但以下設計會提高風險：首頁「熱門主題範本」點名特定 ETF、預設依「勝大盤次數」排序、未來若加入廣告、贊助、券商導購連結。**建議**：範本命名中性化（如「市值型 vs 高股息型」而非「推薦組合」），排序預設採中性欄位（規模或代號），不放任何導購連結；收益模式改變前先確認法規。
- **個人資料保護法**：Phase 2 一旦啟用 Google 登入，就會保存 UID 與 email，需要隱私權政策、刪除帳號流程與事故通報程序。以百人規模來看，**建議 Phase 2 無限期延後**，改用「匯出／匯入設定檔＋分享網址」滿足跨裝置需求。

### 3-6. 首屏 3 秒的主要瓶頸是圖表程式庫，不是資料

規劃書估算 9 檔資料不到 100 KB，但 Plotly.js 完整包是數 MB 等級，遠大於資料本身。**建議**：改用輕量圖表庫，或使用 Plotly partial bundle、延後載入；首屏的預設比較圖由管線預產成靜態 SVG／PNG 直接顯示，互動圖在背景載入完成後再替換。

### 3-7. 資安：真正的攻擊面在 CI 與上游資料

- **CI 供應鏈**：GitHub Actions 持有 Pages／R2 的部署權杖，等於握有網站內容的寫入權。第三方 Action 應鎖定 commit SHA；部署權杖只授權單一專案；`main` 分支加保護；管線依賴版本鎖定。
- **上游資料當作不可信輸入**：ETF 名稱、類別等欄位來自 HTML 解析（SITCA），前端一律以文字節點呈現，管線端也應以白名單字元集驗證。
- 分享網址、匯入組合、自訂圖卡標題的長度與字元限制：同意 Codex。

### 3-8. 存續偏誤與標的池（補充 Codex）

「全體原型 ETF 依月報自動維護」只會收錄**目前仍存續**的 ETF。已清算、合併的 ETF 會從歷史排行中消失，導致年度勝率與平均報酬偏高。同意 Codex 的處理方式；此外，首頁應明示「僅含目前掛牌標的」。

## 4. 對 Codex 意見的逐點回應

### 4-1. 同意並建議直接採納

- 資料授權表、FinMind 不作公開來源、SITCA 欄位取得書面同意後才上線。
- 版本化 manifest：長快取版本檔、短快取 manifest、先驗證整批再切換。
- 首版只用 Pages；R2、Functions、Firestore 等到有實測需求再加。
- 除息資格、XIRR 無解、上市前扣款等反例先手算預期值，**不可用現行 Python 輸出當黃金答案**（否則會把 §2 的缺陷固化成規格）。
- 勝場顯示「勝出／可比完整年度」。
- 分享網址需標明是固定快照還是以最新資料重算。

### 4-2. 建議修正

| Codex 主張 | 我的修正 | 理由 |
|---|---|---|
| 反例 2「XIRR 無唯一解」 | 升級為「求解器從不回報失敗」 | 見 §2-1，影響範圍遠超過同日流量 |
| 每版記錄來源日期、抓取時間、涵蓋率、授權識別、算法版本、內容雜湊；更正紀錄；人工覆核欄位；月工時統計；故障演練 | **分兩級**。上線必要：manifest（資料日期＋算法版本＋檔案清單）、發布閘門、失敗告警、人工事件覆核檔。之後再做：內容雜湊、涵蓋率報表、演練紀錄 | 維護者為單人，且依賴 AI 協助開發。治理流程本身若太重，會比資料錯誤更早讓專案停擺 |
| 首波只開含息趨勢，ETF 排行視完整性再加 | 首波開**含息趨勢＋ETF 年度／滾動報酬**（兩者共用 §3-1 的 `tri[]`）；ETF 規模／受益人等 SITCA 欄位待授權；回測最後上 | 採用 §3-1 後 ETF 報酬幾乎沒有額外計算成本，真正的瓶頸是授權 |
| 單日 ±25% 僅作提示 | 改以官方參考價作必要閘門 | 見 §3-3 |
| 20～30 檔試跑一個月 | 同意，但試跑名單**必須刻意納入**：0050（2025 分割）、至少一檔有現金減資的個股、一檔上櫃債券 ETF、一檔國外成分 ETF、一檔已清算 ETF（驗證歷史頁行為） | 只用一般標的試跑，罕見事件不會出現 |

### 4-3. 回覆 Codex 第 6 節的五個問題

1. **授權證據**：待查。我無法替代官方書面回覆；建議 Phase 0 以「可否公開提供歷史原始值 JSON 下載」為明確問題，逐一詢問 TWSE、TPEx、SITCA、TDCC。**影響範圍**：授權未確認前，前端只發布衍生指數（`tri[]`、`pri[]`），不提供原始收盤價下載。這仍需確認衍生資料是否也受限，但風險較低。
2. **重現反例**：同意且已重現（§2-1、§2-2），並加強反例 2。另提出減資反例（§2-3）。
3. **缺整市場行情／公告撤回**：缺整個市場時不發布新版，manifest 停在前一版並顯示「資料截至 X」；公告撤回時重建受影響標的的完整 `tri[]` 並發新版。固定快照的分享連結在保留期內仍可用，「最新」連結會自動反映更正。
4. **何時引入 R2／Functions／Firestore**：Pages 單站檔案數接近上限的一半時改用 R2（以 §3-1 每檔 1 個檔案計算，650 檔遠低於上限）；有明確的動態 OG 需求且量測 CPU 時間後才引入 Functions；Firestore 建議不引入（§3-5）。
5. **超出單人負擔、最小公開範圍**：個股池 200～300 檔（公司事件人工覆核量最大）、SITCA 月報 HTML 解析（格式改版風險）、Firestore 會員功能。**最小範圍**：約 30 檔 ETF＋10 檔權值股的含息趨勢與 ETF 年度報酬、兩條大盤指數、資料狀態頁。
